Lesson 2: Exploring the platform Library

Module 1 — About This Computer

For teachers. This is the lesson plan: use it to prepare and as your script in class. Students work from the slides, the code files and notebooks, and the practice page. The step-through boxes and runnable code are here so you can try every activity first. How a lesson works →

Time: 75 minutes · Expectations: A1.1, A3.1, A4.3, A4.4, C1.1 · Slides: Lesson 2 slides (press S for speaker notes) · Module 1 overview · Previous: Lesson 1 · Next: Lesson 3

At a Glance

  • Big idea: a module is a toolbox you can explore, and variables let a program remember answers to use later.
  • Students will: list the platform toolbox with dir(), look up a function in the documentation, trace a program that stores answers in variables, see that a variable can be changed, and read two common error messages.
  • Students make: a computer report built from four platform functions stored in variables.
  • Prepare: run l02_report_variables.py and both mistake programs, so you’ve seen the error messages students will see. Open the slides a few minutes before class: Python loads into the browser in the background, and a small “Downloading Pyodide” note shows until it’s ready.
  • After class: Lesson 2 practice, then the Module 1 Assignment.
  • Where it fits: builds on Lesson 1; part of Module 1.

Learning Goals

  • Find out what tools a module contains, using dir() and the Python documentation.
  • Store answers in variables and use them later in a program.
  • Trace which variables exist and what they hold, line by line, including when a variable is given a new value.
  • Read two common error messages and explain what caused them.

Success Criteria

Students can say:

  • I can find a new function in the platform module and use it.
  • I can predict the output of a program that stores values in variables.
  • I can explain what an AttributeError message is telling me.

Review (5 min)

Without running anything, answer in tracing notebooks:

  1. What does platform.machine() print on the classroom computer? On the course web page?
  2. What does the dot in platform.machine() mean? What do the parentheses mean?

Teach: What Else Is in the Toolbox? (15 min)

Open with the problem: “Lesson 1 asked platform three questions. What else does it know about this computer? And how do we make a program remember an answer instead of asking twice?”

A module can contain many tools. dir() lists them. Run it and read the list together.

TipTeacher prompt

Think aloud while reading the list:

  • “Names starting with an underscore, like _comparable_version, are for Python’s own use. We skip those.”
  • “Some names look familiar from Lesson 1: machine, system, node, python_version, release.”
  • “Others are new: platform, architecture, version, uname. The name gives a hint, but the documentation tells us for sure.”

Open the official documentation for the module: docs.python.org/3/library/platform.html. Find platform.machine() and read its description together. Then choose one new function from the list, predict what it does from its name, and try it.

Predict, Then Step (10 min)

This is Lesson 1’s computer report, rewritten so that each answer is stored in a variable before it is printed. Read it without running it, then answer in tracing notebooks:

  1. Which lines ask the computer a question? Which lines print?
  2. What will the first line of output be?
  3. How is this program different from Lesson 1’s program? Will the output be different?

Type your prediction in the box, then press Step to run one line at a time. Watch the Variables panel as well as the output.

TipTeacher prompt: the Variables panel (first use)
  • “Same colours as last lesson: yellow with an arrow is the next line, green just ran.”
  • “There’s a new panel today: Variables. A variable is a name that holds a value. When line 3 runs, watch a new row appear.”
  • After stepping line 3: “Nothing was printed, but something happened. The answer was stored under the name cpu.”
  • “The quotation marks around 'wasm32' tell us the value is text. Python calls text a string. The quotation marks won’t be printed.”
import platform

cpu = platform.machine()
system = platform.system()
name = platform.node()

print("Computer report for", name)
print("CPU type:", cpu)
print("Operating system:", system)

Investigate (20 min)

What the variables hold

Use Back and Step to answer:

  1. After line 3 runs, which variable exists and what is its value?
  2. Lines 3–5 run, but nothing is printed yet. Where did the answers go?
  3. Line 7 uses name, which was created on line 5. What would happen if line 7 came before line 5?
  4. Complete a trace table. Every line that runs gets a row; blank lines don’t. Line 1 is filled in for you.

A variable can change (5 min)

Read this program without running it. What will each line of output be? Then step through it and watch the system row in the Variables panel.

import platform

system = platform.system()
print("Before:", system)
system = "my computer"
print("After:", system)
TipTeacher prompt: changing a variable (first use)
  • “Line 5 uses the same name, system, again. Watch the Variables panel when it runs.”
  • After line 5: “The old value is gone. A variable holds one value at a time; giving it a new value replaces the old one.”
  • “Line 4 already printed the old value, so that output doesn’t change. Python never goes back.”
  1. What does system hold after line 3? After line 5?
  2. Why does the first output line show the operating system but the second doesn’t?

Spot the problem

Each program has a mistake. Predict what will happen, then step through it and read the result carefully.

TipTeacher prompt: reading an error (first use)

After Program B stops:

  • “A red line means Python stopped on that line because of an error. The lines below it never ran.”
  • “The message under the buttons has three parts: the line number, the kind of error (AttributeError), and a description in plain words. Read them in that order.”
  • “Errors aren’t failures. They’re Python telling us exactly where to look.”

Program A

import platform

print(platform.machine)

Program B

import platform

print(platform.cpu())
  1. Program A does not crash, but prints something strange. What is missing?
  2. Program B stops with an AttributeError. Which line caused it? What is the message telling you?
  3. How could dir(platform) have prevented the mistake in Program B?
  4. If time allows: run Program B on the classroom computer. How does the full error message there show the same information? (Otherwise, students meet the full message in Make.)

Modify (10 min)

Add two more facts to the report. For each one, create a variable and print it with a label.

  1. The Python version: platform.python_version()
  2. The operating system’s version number: platform.release()

Make: My Computer Report (10 min)

On the classroom computer (Thonny, IDLE, or VS Code), write a computer report that uses four platform functions, including at least one you found with dir() or the documentation. Store each answer in a variable with a clear name, then print a labelled report. Students save it as my_report.py in ics3u/module-01/lesson-02/. This is practice for the assignment’s Part B, so make sure everyone writes and runs at least two lines before the bell. Early finishers can paste it into the Modify box above and compare the browser’s answers.

Check: Exit Ticket (5 min)

Suppose this program were run on a Windows laptop with an Intel processor.

import platform

cpu = platform.machine()
print("CPU:", cpu)
print("Again:", cpu)
  1. What would the output be? Write it exactly.
  2. How many times does the program ask the computer for its CPU type?

After the Lesson

  • Students do the Lesson 2 practice: trace a program that changes a variable, fix a mistake, and use a function they found with dir().
  • Suggested hand-in: the Make program’s .py file with its output pasted as a comment at the bottom. Check trace tables in tracing notebooks as you circulate.
  • Students then start the Module 1 Assignment, the Computer Report Card.
  • Read the exit tickets. Students who answered “twice” to question 2 still think a variable re-asks the computer; revisit the trace table.

Teacher Notes

  • Variables. A variable is a name that stores a value. cpu = platform.machine() asks the question once and keeps the answer, so the program can use it later, as many times as needed.
  • Step-through box. It runs the real program in the browser, so platform works and the variables hold the browser’s answers ('wasm32', 'Emscripten'). Python Tutor is not used here because it does not allow the platform module.
  • Changing a variable. Introduced briefly, through reading only: a variable holds one value at a time, and a new value replaces the old one. Students trace it again in the practice and in Assignment Part A. Updating a variable from its own value (count = count + 1) comes later, when programs start calculating.
  • dir() output is long and includes names starting with _; tell students to skip those. In the browser and on the classroom computer, the lists may differ slightly between Python versions.
  • Spot the problem. Without parentheses, platform.machine is the tool itself, not its answer, so Python prints a description of the function, e.g. <function machine at 0x104cb3e20>. The AttributeError says the module has no tool by that name. The step-through box highlights the line that caused the error and shows the error type and message; Thonny, IDLE, and VS Code show the same information as a full traceback, which students should learn to read too.
  • Slides. Open the slides on the projector and this plan on your own screen. Press S in the slides for speaker view.
  • Spiral. Students now write variables and read error messages. Calculating with values (os.cpu_count(), storage in gigabytes) comes in Module 2.
  • Answers are in the answer-keys folder of the course’s GitHub repository, not on this site.
