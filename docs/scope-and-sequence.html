Scope and Sequence

ICS3U — 110 hours, Python 3

Note

Draft. Module order, hours, and expectation coverage are proposed and open to revision.

How This Course Is Organized

This is a spiral course, not a sequence of topic units. Students do not spend weeks on output, then weeks on input, then weeks on decisions. From the first week, they read real programs that already use output, input, variables, decisions, loops, strings, and lists. Each module comes back to all of these ideas at a deeper level.

  • Modules are built around themes and anchor programs, not single programming constructs. Each module has a purpose students can see (find out about this computer, check whether it meets a need, measure how fast it is, keep passwords safe, troubleshoot the network, investigate data).
  • Reading makes early depth possible. Students can read and predict code that uses a loop or a list weeks before they are asked to write one. When code uses something not yet taught, the teacher explains it briefly and moves on: “You’ll learn to write these properly later.”
  • Each idea moves through four levels across the course: read it, modify it, write it, then design with it.
  • Not project-based. Lessons stay teacher-led and structured (see the teaching approach); a full independent project comes only at the end.

Course at a Glance

The course runs 110 hours, roughly 88 periods of 75 minutes. Hours are a guide. Every module is about the computer students are sitting at, the way they use it, or the world it connects to.

R = Read: meets it in programs students read, predict, and trace. M = Modify: changes existing code that uses it. W = Write: writes new code with it. D = Design: chooses and combines it in their own project.

The Toolkit Thread

Students keep one folder, My Computer Toolkit, for the whole course. Each module’s assignment adds a part, so students keep reopening and improving their own earlier code instead of starting fresh. From Module 4 on, toolkit files import functions from each other.

Module Adds to the toolkit Skill level
1 report_card.py: facts about this computer Read and modify
2 drive_check.py: storage and core checks with warning levels Write
3 benchmark.py: a benchmark suite as functions Write
4 password_tools.py: the first module of the student’s own reusable functions Write and reuse
5 network_check.py, which writes network_log.csv Combine; write files
6 folder_detective.py and backup.py, which also analyze the Module 5 log Extend and combine
7 The class’s “Lab Health Check” assembles everyone’s toolkits; individual projects may build on them Design

Practising the Basics

A spiral brings every idea back, but basics also need practice until they’re automatic. Each module has:

  • A Skill Builder page: short drills on the module’s basics and earlier ones (predict the output, fix the error, Parsons problems, fill in the blank, write a tiny program). Drills can be plainer than lessons; not every exercise needs to be about hardware.
  • Quick Builds: two small graded programs before the module assignment, such as a system banner and a parts receipt in Module 1, or a file name cleaner in Module 4. Each is the Make product of a named lesson, so it costs no extra class time.
  • A work period: in Modules 1–6, the period before the test is a short review followed by class time for the module assignment.
  • Spaced warm-ups: every lesson’s review includes a question from two or more lessons back, often an earlier module.

Course Tools

  • Sample folder generator: make_sample_folder.py builds a realistic, messy folder for file lessons: text, CSV, Python, and log files, real PNG images, zip archives, sub-folders, awkward names, duplicates, and backdated files. It uses only the standard library. With a fixed seed every student gets the same folder, so answer keys have exact answers; --seed gives each student a different one. It deletes only inside folders it created itself, so students can rebuild after a mistake. Planned: an optional --download that adds real, licence-checked files hosted on this site, falling back to local generation if the network blocks it. Used in Modules 1, 5 (reading its download code), 6, and 7.

Modules

Each module’s overview page has its planned lessons, anchor programs, and assignment. This section is the summary.

Module 1 — About This Computer (15 h)

Purpose: Ask the computer about itself.

Anchor programs: a two-line program that prints the CPU type (platform.machine()); a labelled computer report built from the platform module and stored in variables; a greeter that asks the user’s name and gives a hardware summary; a report that loops through a list of facts.

Pacing: one library first. Lessons 1–4 use only platform, starting from a single line; sys appears in Lesson 5 and os (for paths) in Lesson 6. os.cpu_count() and shutil wait until Module 2.

  • Taught explicitly: what a program is; reading and predicting output; import and calling a module’s functions; print() in depth (arguments, sep, end, escape characters) and f-strings with padding; variables and the basic types (str, int, float, bool) and converting between them; simple arithmetic and :.2f; input(); tracing line by line; finding tools with dir() and the documentation; comments and naming conventions; paths, the current folder, and running a program from the terminal; syntax, run-time, and logic errors, reading a traceback, and a debugging routine
  • Met through reading: if/elif/else, a for loop over a list
  • Computer science: CPU types and operating systems; where code runs (classroom computer, browser, cloud); where variables live (RAM) and where arithmetic happens (CPU); source code vs. machine code (bytecode with dis); interpreters vs. compilers; applications, languages, and operating systems; organizing program files

Quick Builds: System Banner, Parts Receipt. Assignment: Computer Report Card. Expectations: A1.1, A2.1, A2.2, A3.1, A4.1, A4.2, A4.3, A4.4, C1.1, C1.4, C2.1, C3.1, C3.3, C3.4, C3.5

Module 2 — Spec Checker (15 h)

Purpose: Decide whether a computer meets a user’s needs.

Anchor programs: a core counter (os.cpu_count()); a storage calculator (why “1 TB” shows as 931 GB); a drive gauge (shutil.disk_usage()); “Will this game run?”; a monitor sharpness (pixels per inch) calculator.

  • Taught explicitly: input and type conversion; data types; arithmetic, integer division, remainder, order of operations; comparison and logical operators; if/elif/else; try/except for bad input; user-friendly prompts and messages; test plans with normal, boundary, and invalid cases
  • Met through modifying: a loop over a list of requirements; .strip() and .lower() for cleaning input
  • Computer science: internal components, specifications, and peripherals related to user needs; the input-process-output model

Quick Builds: Storage Unit Converter, Battery Life Estimator. Assignment: Will It Run? Expectations: A1.1, A1.3, A1.4, A2.1, A2.2, A4.1, A4.3, A4.5, B1.1, B1.3, B2.5, B3.2, B3.3, B4.4, C1.1, C1.2, C1.3

Module 3 — Benchmark Lab (14 h)

Purpose: Measure how fast the computer really is.

Anchor programs: count to a million with a stopwatch; a benchmark suite (counting, string building, checking primes); a study timer; a reaction timer; “Is shuffle really random?”; a typing speed test.

  • Taught explicitly: for loops and range(); while loops; counters and accumulators; nested loops and decisions; the time and random modules; reading and modifying first functions; flow charts and pseudocode; program skeletons; debugging by tracing and printing variables
  • Met through modifying: a list of counts; random.shuffle(); strings in prompts and messages
  • Computer science: benchmarks and fair tests; how CPU type, cores, and the interpreter affect speed; running the same code on different machines; determining primes

Quick Builds: Download Time Table, Study Timer. Assignment: Typing Speed Test, with a benchmark report. Expectations: A2.2, A2.3, A3.1, A3.2, A4.1, A4.4, B1.1, B2.1, B2.4, B3.2, B4.5, C1.2, C1.4

Module 4 — Passwords and Secret Messages (15 h)

Purpose: Learn how computers store text, and keep it safe.

Anchor programs: a binary and hex converter; a Unicode inspector; a password strength checker; a crack-time estimator (using Module 3’s benchmark); a Caesar cipher (short activity) that shows why simple ciphers aren’t secure.

  • Taught explicitly: strings as sequences (indexing, slicing, traversal, methods); ord() and chr(); writing functions with parameters and return values; local and global scope; reusable modules; secrets and hashlib
  • Computer science: binary, hexadecimal, ASCII, and Unicode; how websites store passwords; cryptography as a research area; malware and a system protection plan

Quick Builds: Username Maker, File Name Cleaner. Assignment: Password Toolkit, with a home system protection plan. Expectations: A1.2, A3.1, A3.2, A4.1, B1.1, B2.3, B4.4, C2.2, D2.1

Module 5 — On the Network (14 h)

Purpose: Find out how the computer talks to the rest of the world.

Anchor programs: “Who am I on the network?” (host name and local IP address); an IP address explainer (list of octets in binary, private or public); a website lookup (DNS); a response timer; a download speed test.

  • Taught explicitly: lists as one-dimensional arrays (elements, indexes, bounds); .split() and .append(); count, total, highest, lowest; exceptions for network failures; testing with good, slow, and broken inputs; writing files (a CSV log with timestamps); socket, ipaddress, urllib, and datetime
  • Computer science: IP addresses, DNS, ports, packets, and routers; private and public networks; firewalls; running a web server; distributed computing; data flow diagrams

Quick Builds: Speed Log Summary, Web Address Splitter. Assignment: Is It Me or the Wi-Fi? Expectations: A1.2, A1.5, A1.6, A2.3, A3.1, A3.2, A4.5, B1.1, B2.4, B3.3, D2.1

Module 6 — Data Detective (15 h)

Purpose: Investigate data about the computer and its use.

Anchor programs: a folder detective on a generated sample folder (files by type, total size, biggest, oldest, duplicates); a top-ten list of the biggest files kept in sorted order; a backup maker that verifies copies with hashes; an analysis of the students’ own Module 5 network log; the computer lab’s yearly power bill from a CSV file.

  • Taught explicitly: lists and parallel lists; linear search; highest and lowest value; inserting into a sorted list and deleting from the middle; reading CSV files; breaking a program into functions; structure charts; describing and comparing designs; testing with a full range of cases
  • Computer science: organizing files and folders; backing up and archiving (the 3-2-1 rule); environmental and health effects of computer use; reducing them; e-waste, refurbishing, and community partners

Quick Builds: Extension Report, Duplicate Finder. Assignment: Folder Detective. Expectations: A1.5, A1.6, A2.3, A3.2, A4.4, A4.5, B2.2, B2.3, B2.4, B3.1, C2.1, C2.3, D1.1, D1.2, D1.3, D1.4

Module 7 — Software Development Project (16 h)

Purpose: Plan, build, test, and present a useful program for a real person.

  • Part 1, teacher-led class project (about 4 h): “Lab Health Check”, built by teams from earlier modules’ code; the software development life cycle, a Gantt chart, and milestones practised together
  • Part 2, individual or pair project (about 12 h): a real user; specification by interview or questionnaire; design documents; test plan first; written status reports; presentation
  • Design level: students choose and combine every idea from the spiral

Expectations: A4.2, A4.5, B1.2, B2.1, B2.2, B2.3, B2.4, B2.5, B4.1, B4.2, B4.3, B4.4, B4.5, B4.6, C3.2

Computer Science in the World (6 h, between Modules 2–6)

Purpose: See where computer science leads.

Five short lessons, each placed after a module and tied to it (careers in hardware after Module 2, distributed computing after Module 3, security after Module 4, collaborative research after Module 5, postsecondary programs after Module 6), plus a research report submitted in stages.

Expectations: D2.1, D2.2, D2.3, D3.1, D3.2, D3.3, D3.4, D3.5

Assessment Overview

Following Ontario’s Growing Success policy: 70% of the final grade comes from evaluations during the course and 30% from final evaluations.

  • Every lesson: an exit ticket, usually a code-reading or tracing question (assessment for and as learning, not counted toward the grade).
  • Within each module: short quizzes, two Quick Builds (small graded programs), and the module assignment, which adds to the student’s toolkit.
  • End of Modules 1–6: a module test that always includes a code-reading and tracing section and a short basics section. Because the course spirals, every test may include earlier ideas.
  • Computer Science in the World: the staged research report.
  • Final 30%: the Module 7 software development project and a final exam that includes code reading and tracing.

Python Notes for Teachers

The 2008 curriculum uses general terms. In Python:

  • Constants (A1.1) are a naming convention (UPPER_CASE); Python does not enforce them.
  • One-dimensional arrays (A1.5, A1.6) are taught as Python lists, used with a single data type and fixed purpose.
  • Procedures (A3.2) are functions that do not return a value.
  • Compiler error messages (A4.3) appear in Python as tracebacks; C3.4 contrasts Python’s interpreter with compiled languages such as C or Java.
  • Hardware and network programs use only the standard library (platform, then os, shutil, time, socket, ipaddress, and urllib). Network programs need a real computer: the site’s browser boxes can’t open network connections. Results depend on where the code runs: macOS reports itself as “Darwin”; the course website’s runnable code reports a browser virtual computer (wasm32, Emscripten); Google Colab reports a Google cloud server (typically x86_64, Linux). These differences are a deliberate teaching point. Use platform.machine() for the CPU type; platform.processor() is unreliable across systems. Total RAM is not available from the standard library.

Teaching Approach

Every lesson follows the course’s reading-first approach: students read, trace, and predict code before they write it. Each lesson opens with review and a useful problem (“How could we check 500 files without opening each one?”), then moves through a teacher-led worked example, then Predict, Run, Investigate, Modify, and Make (PRIMM). Writing new code from scratch always comes after reading and modifying.
